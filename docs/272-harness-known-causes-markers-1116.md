## 1. Known third-party causes: VOID + one relaunch instead of a lost job

Two Apex Radiance 4.0.1 bugs cost jobs on 2026-11-16: the device-creation crash (docs/270 §29) and the Present lock cycle at world load (docs/67 §38). Both are Apex's [verified in those sections]; until a fixed Apex ships, a hit should not cost the job.

- Table `tools/harness/known-causes.json` (matcher `tools/harness/known-causes.ts`): id, kind, owner, upstream link, doc, the match rule and real-line `cases` (match / weakMatch / noMatch) that `--self-check` runs.
  - `apex-0010-backbuffer` (crash): exception type starts `ACCESS_VIOLATION reading from address 0x00000000`, fault module `d3d9.dll`, RVA `0x2d4b4`. Seen in sv-m1-gcnat (queue mono-measure-memgaps-1115-mm, 04:02:21) and rerun 10 step 1 (19:03:00 on 11-15); both reports give base + 0x2D4B4 [verified: module list of both xcpt files].
  - `apex-401-present-lock-cycle` (hang): a kill dump whose lock cycle has every lock and every lock call in `ApexRadiance.asi`. Upstream: https://github.com/loinyx/Sims3-ApexRadiance/issues/90 (start-up deadlock).
- Rule "ours until proven": only these exact signatures count; any other crash or hang stays CRASH / FAIL.
- Crash RVA: `crash-ledger.ts` triage now prints `at 0x7208d4b4 in d3d9.dll+0x2d4b4`, the RVA from the report's own module list (the `base ... size ...` line whose path is the fault address's path, so Bin's d3d9.dll is never confused with system32's). A report without that line prints no RVA; the matcher then compares the low 16 bits of the address only (module bases are 64 KB aligned) and the row says `weak match: low 16 bits of the address only, the report had no module base`. The two crash lines already in the chain .out files predate the RVA and match weakly [verified: `node tools/harness/known-causes.ts probe-out/queue/chain-night-rebaseline-1115-mono.out`].
- Hang modules: `tools/dump-locks.ts` now names the module of each cycle lock and of each lock call (first return address near the stack top in a non-system module's executable section, read from the PE section table in the dump) and appends `; cycle modules: <list>` to its summary. On the real bp-jitsmall-b6 dump: `cycle modules: ApexRadiance.asi (locks ApexRadiance.asi+0xC7ECD8, ApexRadiance.asi+0xC7FF28; callers ApexRadiance.asi+0x560C73, ApexRadiance.asi+0x476402)` [verified: run on `ts3w-51352-20261116T005126.dmp`; +0x560C73 is the lock helper's return named in docs/67 §38]. A heap lock prints a bare address and an unknown caller `?`, so neither can match a one-module rule.
- queue.ts: after the EA package-lock retry check, a match marks the row `VOID: known cause <id> (<owner>): run void, relaunched once as <id>-kc; <upstream> (<doc>)` (results md status **VOID**, run-verdict.ts reads it as VOID through "run void"), keeps the old FAIL lines as `first attempt (known cause): ...`, and queues `<id>-kc` next (fresh start: never kept for a rewind or reuse session). A VOID row does not set the exit code, does not trigger `stopQueueOnFail` or the crash stop. A hit on the relaunch is a normal CRASH/FAIL row with a `note: known cause <id> again on the relaunch` line; a crash there follows the crashed VOID row, so today's "two jobs in a row crashed" stop applies. Jobs with `expectHang` and jobs already retried for the EA package lock are never relaunched.
- Also fixed in passing: a rewind group could keep the game of a job whose EA package-lock retry cleared `row.error` (`rwKeep` now also checks `retriedAs`).
- Not covered: the measurement smoke job (its own STOP path), and crashes with no EA xcpt report (no module, no RVA).

## 2. Chain echo lines that never reached the .out; chain markers

- Cause [verified: repro with a temp chain script, now in `track.ts --self-check`]: `track.ts switch` opened the .out with Node's `openSync(f, 'a')` and gave that handle to Git Bash as stdout. That handle has FILE_APPEND_DATA but not FILE_WRITE_DATA; MSYS programs (bash's own `echo`, `tee`) fail to write to it without any error, native programs (node, python) succeed. So `chain-mono-rest-rebaseline-1116.out` held only the node lines (builds.ts checks, turbo-compat `state apex`) and none of the chain's `echo` lines, and nothing a chain piped through `tee` either. Not buffering, not a tee subshell.
- Fix: `startChain` lets bash open the .out itself (`exec >>"$out" 2>&1 </dev/null; exec bash "$script"`), so every child inherits an MSYS append handle; earlier .out content stays (append). The self-check starts a real chain script with echo, tee, node and marker lines and requires all of them in order.
- Markers: `node tools/harness/track.ts marker "<text>"` prints `marker: <UTC time>Z <text>` (lands in the .out) and appends `<UTC time>Z <text>` to `probe-out/queue/<chain>.markers`; the chain name comes from `TS3_CHAIN` (set by `switch`) or `--chain <name>`; without either the line is printed with a WARN and the chain goes on. `node tools/harness/track.ts wait-marker <chain> "<text>"` blocks until a marker line contains the text (exit 0) and exits 3 when the chain process is gone without it (the failure mode of today's handover). New chains: handover lines through `marker`, waiters through `wait-marker` (or `wait-chain` when they need the whole chain gone). Chains already running keep the old start; this applies from the next `switch`.

## 3. Queue key `rewindGroupBySave`: group jobs by start key for rewind reuse

- Why: the queue-rewind dry run found 773 of 1900 neighbouring job pairs that differ only by save, so most queues alternate BP / IP / SV and never get two equal starts in a row (no rewind group).
- `"rewindGroupBySave": true` (queue level, default off; anything but a boolean is refused at parse): queue.ts reorders the whole job list before `--from` / `--only` (so a `--from <id>` resume continues the grouped order) with `groupBySave` (`tools/harness/queue-rewind.ts`): between two barriers, jobs with the same rewind start key (queue.ts keyOf with the rewind ini, i.e. same asi, ini, packages, save, configs) go next to each other, keys in the order of their first job, each key's jobs in their own order (an ABBA order inside one save stays). Barriers keep their place and nothing moves across them: a job that cannot start from a rewind (`rewindBlock`: scripts, matrix, saveReload, travel, story, `rewind: false`, no ts3native, ...), a `stopQueueOnFail` gate, a smoke job (id contains "smoke"). Queue jobs have no `after` / dependency key today [verified: JOB_KEYS, 0 queues use one], so these barriers are the only order constraints.
- Dry run: every `queue.ts --dry-run` prints `rewindGroupBySave on|off: A -> B of N jobs start from a rewind when grouped (+K, ~M min; J jobs move)` (rewind assumed on; minutes at the 120 s fresh vs 8 s rewind estimate); with the key on it also prints the new order. Example, `rebaseline-apex401-1115.json`: `0 -> 29 of 32 jobs ... (+29, ~54 min; 30 jobs move)` [verified: dry run].
- Caution: grouping changes the time interleaving of separate-load timing arms (that queue's on/off arms share one key and differ only by the chain's Bin state, run per block with `--only`). Leave the key off where interleaving is the design (ABBA blocks across saves for drift); it is for correctness queues and repeats.

## 4. Per-arm ms/s, p99 / p99.9, max and hitch counts in the results md

- What the profile already records [verified: arm-ms.ts and hitch-ab.ts on `mono-measure-equalsfast-1115-mm-2026-11-16-bp-iclock-eqfast-ab` and `mono-jitsmall-time-1115-mm-2026-11-15-bp-jitsmall-time`]: `<tag>-<secs>-seconds.csv` (per second iterations and script / route / animPose / locomotion / taskObjects / threaded ms, plus the `arm` column after an `--ab` run) and `<tag>-<secs>-hitches.jsonl` (every iteration >= 50 ms). `rng-compare.ts` has no per-arm data (seeded vs unseeded run metrics only), so it is not used. Before this change the md row had none of these numbers (the eqfast-ab row shows verdicts, memory and `timing: invalid (...)` only).
- Each profile row (and each `profile.repros` window) now ends with one line per run: `sim ms/s off 212.7 / on 210.8 (on - off -1.9, -0.9%); off: p99 95 ms, p99.9 153, max 218, >=300 0, >=1000 0 (2.4 min); on: ...` (a run without arms: `sim ms/s 72.4; p99 542 ms, ...`). sim ms/s = the sum of script, route, animPose and locomotion ms/s exactly as `arm-ms.ts` prints it; the hitch numbers are `hitch-ab.ts` arm stats (same arm split and exclusions; p99 below the 50 ms hitch floor shows as `<50`). Both read the files only; a run with no seconds.csv adds nothing, no hitches.jsonl says `no hitch files`. The same data goes to the jsonl row as `armMs`.
- End of the results md: `A/B summary of this run` with one line per job group that has both arms (in-load `--ab` arms per job; separate-load `<name>-off-N` / `-on-N` jobs pooled as `<name>`, as `arm-ms.ts` groups them): pooled ms/s (weighted by seconds), on - off and %, and >= 300 / >= 1000 ms per 10 min per arm (`?` when a run of that arm had no hitch files). It states numbers only; the 3-5 ms/s ON rule stays a reader's decision.
- Not done: the timing verdict's validity (`timing: valid|invalid`) is unchanged and still decides whether the numbers count as timing evidence.
