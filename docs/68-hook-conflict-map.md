# Hook conflict map: every patched TS3W.exe address

Written 2026-10-16. Static only: no game run. Steam 1.67 `TS3W.exe` (SHA-256 prefix `10b2423e`), image base `0x400000`, `.text` `0x401000`-`0xF94FFF`.

One table of every address in `TS3W.exe` that a native plugin in our install patches or detours, plus our planned sites, then the overlaps, install order, late patches and a rule for new hooks.

Sources, and how sure each is:
- **ts3native:** `native/ts3native/*.cpp` (read 2026-10-16). `node tools/hook-sites.ts` lists every code-range literal in those sources, and `--check` fails when one is missing from this doc [verified].
- **S3SS 1.6.3:** docs/03 §1 (source read at `5eb2c65`, patterns re-run on Steam 1.67), the S3SS log of a 2026-10-16 start (`<Documents>\Electronic Arts\The Sims 3\S3SS\S3SS_LOG.txt`, lists every address it patched) and our `S3SS.toml` (`tools/setup/fixes.json` `s3ss-config`) [verified].
- **S3PP (Sims 3 Performance Patch) 2.1:** docs/17 §8 (1.1 source signatures re-run on Steam) and the 1.1 source in `game-copy/s3pp` [verified].
- **MonoPatcher 0.3.0:** docs/06 §0.2/§1 (8 signatures, each one hit on Steam) [verified]; a signature scan of the installed `.asi` against `TS3W.exe` hit `0xD7DB80` and `0xE5637D` again [verified].
- **TS3Patch.asi (Smooth Patch) and D3DShaderReplacer.asi:** static import, string and byte scans of the copies in `game-copy/bin` [verified scans; meaning inferred where marked]. Neither is in the current `Game\Bin`. The installer removes TS3Patch (`smoothpatch-asi`, `remove-if-present`), and D3DShaderReplacer is only in the 2026-10-11 copy.
- **Planned:** docs/60 §2.2 (H6 closures), PLAN.md "Next round: fixes from the mapping waves" (numbers `#n` below), docs/30 §3-§4 and PLAN.md "`[MonoThread]` step 2" (P3/P4).

Kinds: **detour** = `jmp` written over a function entry (ts3native `InstallDetour`, MinHook or MS Detours); **mid** = `jmp` in the middle of a function; **call** = the rel32 of one `call` retargeted; **imm** = an immediate or opcode byte rewritten; **slot** = a data pointer swapped; **read** = only resolved, called or hashed, never written.

## 4. Overlaps

"Same bytes" = the written ranges overlap or are within 16 bytes. "Signature window" = our write lands inside the bytes another plugin pattern-matches before it patches, so its patch fails to install even though it writes elsewhere. ## 5. Install order and late patches

| Plugin | Where it patches | When | Sees ours? |
|---|---|---|---|
| ts3native | `DllMain`, main thread | before the exe entry point (UAL loads plugins at start-up, docs/15) | - |
| MonoPatcher | `DllMain` (MinHook) | start-up; ForceJIT bytes later, on demand [inferred] | its sites are not ours |
| S3SS | its own "Hook thread" (log: `Hook thread started` precedes every patch line) | start-up, from a second thread; settings and D3D9 hooks later (device creation) | yes: it scans after or concurrently with our `DllMain` [verified log order; exact interleaving inferred] |
| S3PP | its own worker thread, priority order | while the game keeps starting (docs/17 §8.1) | yes: after our `DllMain` |
| TS3Patch, D3DShaderReplacer | own thread (`CreateThread` imported), MinHook freeze | after the game window or device exists [inferred] | n/a |
| ts3native route worker | `runtime_invoke` slot `0x1195B60` | first worker plan (in game) | atomic compare-exchange |

Consequences:
- Our checked-bytes rule protects **us** (a foreign `jmp` makes ours `SKIP`), but because we install first, it is the third-party plugin that meets our `jmp` and fails. S3PP refuses cleanly (expected bytes); S3SS's behaviour on a failed helper pattern is not known [inferred]. So a new ts3native hook can switch off a community patch without any error in our log.
- UAL loads ASIs in directory order (`MonoPatcher`, `Sims3Performance`, `Sims3SettingsSetter`, `ts3native`) [community: UAL design], but the S3SS and S3PP patch threads are not ordered against our `DllMain`. Never rely on order.
- Late code writes made while other threads run: S3SS hook thread, S3PP worker, MonoPatcher ForceJIT, and (if reinstalled) the MinHook-based TS3Patch and D3DShaderReplacer. MinHook freezes threads and moves instruction pointers out of the patched bytes; MS Detours (S3PP) only does that for threads passed to `DetourUpdateThread`, and S3PP passes only its own [verified source for `localized_string_cache.cpp`]. A 5-byte write over code another thread is executing is a crash source to keep in mind during start-up crashes [inferred].

## 6. Rule for new hooks

1. **Look it up first.** Before choosing a site, find it and its function in this table and run `node tools/hook-sites.ts --check`. The same commit that adds the hook adds its row here (`--check` fails otherwise).
2. **Stay out of signature windows.** Do not write inside the bytes another plugin pattern-matches, not only the bytes it patches: S3SS and S3PP patterns (docs/03 §1, S3PP source), MonoPatcher signatures (docs/06). Hook the callee entry, a caller, or a data slot instead. Known windows: `0xD81FC3`-`0xD81FE0`, `0x59C5B0`+12, `0xE4D9F0`+34, the four S3PP seam entries, and the S3SS lot streaming helpers (§1.1).
3. **One stub per address.** A second user of an address (a fix and a Verify probe) goes through the owner's stub and counts from inside it; never stack two of our detours.
4. **Skip when a foreign jump is present.** `InstallDetour` already refuses changed bytes. A new hook logs what it found (`E9`/`EB`/`FF 25` = foreign hook, with the module that owns the target) and stays off; it never chains onto a foreign `jmp` by hand.
5. **Install in `DllMain` only.** No code writes after start-up; a late change is an atomic swap of a data pointer, like the `runtime_invoke` slot.
6. **Coordinate with the mod when we must share.** If our fix replaces a community patch (#3), the installer turns that patch off in its config and ts3native refuses to install while the mod's switch is on, so both can never be live.
7. **Prove the community patches still install.** A run with the new switch on must show the S3SS lines (`Object throttle installed`, `SmoothPatchPrecise ... Successfully installed`) and the S3PP lines (`four scheduler seams armed`, `[STBL509] active`, `[MTEH] ... armed`) in their logs. A missing line is a failed run under the stop-on-error rule.

## 7. Porting addresses to another exe build

Every address here is for the Steam TS3W.exe 1.67, the only exe we support. To port a fix to another build (EA app / Origin 1.69 or a later patch), start from an address map instead of re-finding each site:

```
node tools/exe-addr-map.ts --other "<path>\TS3W.exe" [--ref game-copy/bin/TS3W.exe] [--addrs sites.txt] [--all]
```

- Default address list = every code address our native sources name (`tools/hook-sites.ts`); `--addrs` takes one hex address per line with an optional label.
- Per address it takes a byte window of the Steam exe, turns relocated dwords (`.reloc`) and call/jmp rel32 operands into wildcards, searches the other exe's code sections and grows the window until one match is left. Kinds: `exact` (same bytes), `masked` (unique with wildcards), `near` (ambiguous, one candidate shares the nearest unique neighbour's delta), `offset-changed` (unique, but a displacement or immediate in the window differs: §7.2), `ambiguous N`, `missing` (with a neighbour-delta `hint`). Data and code pointers read by matched code (globals, IAT slots, call targets) are mapped too (`ref` rows with votes; `ref-conflict` = the copies disagree).
- It prints a summary line and only the problem rows; the full map goes to `out/exe-addr-map/<exe>.csv` (gitignored: it is derived from EA bytes, never commit it). `.json` for `--out` writes JSON.
- Treat `masked` and `near` as [inferred] until the patch's expected-bytes check passes on the new exe; `missing` and `ambiguous` need a manual look (start at `hint`). `funcOff` (offset from the function start) is a padding-based guess.
- Steam vs Steam (2026-10-31): 857 of 857 addresses `exact` at the same address, 212 refs, 0 conflicts, ~3 s.
- Limits: the Steam exe has no `.reloc`, so absolute pointers inside code are not wildcarded by the plain match (the fuzzy pass of §7.2 covers them); no string or import-name anchors; a function the other build recompiled differently (other register allocation, inlining) shows as `missing`; data addresses are only found when a matched window reads them.

### 7.1 Address macro codemod (`TS3A`)

Today every address in ts3native is a plain hex literal, so a port means editing each one. `tools/addr-codemod.ts` does that refactor mechanically (not applied yet: the refactor waits until after Mono, docs/23 #18):

```
node tools/addr-codemod.ts                 # dry run: counts per file, unsure rows; all rows -> out/addr-codemod/scan.csv
node tools/addr-codemod.ts --apply         # 0x00D7E560 -> TS3A(0x00D7E560), idempotent; adds ts3addr.h to ts3native.cpp
node tools/addr-codemod.ts gen --map out/exe-addr-map/<exe>.csv [--allow-inferred]
```

- Scope: `native/ts3native/*.cpp|*.h` without tests and generated headers (`vcallsites*.h`: fix their generator). Literals in the Steam 1.67 code range (the `hook-sites.ts` range) or `.rdata`/`.data`/`.tls` (IAT included) from the exe's section table; comments and strings skipped.
- Kinds: `wrap`; `unsure` (page-aligned values = section bounds, sizes or the base; all-F masks; the FNV prime; size/mask/count names next to it): decide by hand; `manual` (case labels, inline asm, `#if`, inside `[]`, template arguments): left as literals.
- `native/ts3native/ts3addr.h`: `TS3A(x)` = `(x)` by default, so the Steam build stays byte-identical. With `/DTS3A_TABLE` it is a constexpr binary search over `native/ts3native/out/ts3addr-table.h` (written by `gen`, gitignored, derived from EA bytes), forced to compile time: static initializers stay constant and an address missing from the table fails the build.
- `gen` takes only `exact`/`masked` rows; `near`, `offset-changed` and `ref` rows (data addresses) need `--allow-inferred` and stay [inferred] until the patch's expected-bytes check passes; `missing`, `ambiguous` and `ref-conflict` always fail.
- Scan 2026-10-31: 1,393 literals to wrap (1,027 distinct addresses: code 1,210, `.data` 153, `.rdata` 94 literals), 47 unsure, 17 manual (12 case labels in `apex.cpp`, 5 inline asm in `mintcall.cpp`); 4 generated headers skipped (5,917 rows). A trial `--apply` (reverted, not committed) rewrote 79 files and a second scan found 0 left to wrap.
- Limits: addresses built at run time (base + offset), the generated headers and the manual rows still need a hand port; `monohost` and `worldimage` are not scanned; byte identity and the `TS3A_TABLE` header are not yet compile-checked.

### 7.2 Struct offsets and vtable slots (same run)

`exe-addr-map.ts` also diffs what a moved address alone does not show (`tools/exe-port-diff.ts`, decoder `tools/x86-len.ts`: table-driven x86-32 length, ModRM/SIB displacement, immediate and branch operand positions, no npm deps):

- **Fuzzy match:** when no window matches, the window is searched again with every decoded displacement, immediate and branch operand wildcarded too; a unique hit is kept. The plain mask only covers `.reloc` dwords and call/jmp rel32, so a function whose only change is a field offset used to come out `missing`.
- **Offset diff:** every mapped site's window (plus the site's first 16 bytes, since a one-sided window can end at the site) is decoded in both copies at the same positions, until the first instruction that decodes differently. A non-absolute displacement or a non-pointer immediate that differs makes the row `offset-changed`. Rows are grouped by (kind, old -> new) with counts and sites, so a shifted struct field (`disp 0x918 -> 0x91C`) is one line: `out/exe-addr-map/<exe>.offsets.csv`.
- **Vtable slot map:** vtables = runs of >= 2 aligned dwords outside code pointing at function starts (int3/nop/ret padding before them; `.reloc` entries instead when the exe has them). Functions are paired by a unique masked 24-byte prologue among vtable targets plus the address map's own rows, each vtable is mapped by majority vote (vtable, slot shift), ties broken by same length then the median code delta; a vtable without votes takes the nearest mapped vtable's delta when a vtable of the same length sits there (votes 0 = inferred). Slots without a mapped function take the shift of agreeing neighbours. The vtables our sources name (any literal inside one, via the `addr-codemod.ts` scan) are printed when shifted, resized or unmapped, with each named slot's new address: `out/exe-addr-map/<exe>.vtables.csv`.
- Steam vs Steam (2026-10-31): 0 offset diffs; 2,099 vtables, all mapped to themselves with no slot shift (264 by neighbour delta, 178 after a tie-break); 26 named by our sources, 0 shifted; ~4 s for the whole run.
- Limits: a displacement that changes size (disp8 `0x7C` -> disp32 `0x80`) changes the instruction length and stays `missing`; RTTI is not used; slot offsets used in our sources (`[reg+0x60]` call patterns) are not scanned, only literal vtable/slot addresses.

### 7.3 Expected original bytes (`tools/patch-bytes-check.ts`)

ts3native checks original bytes before every write (`Matches`, `InstallDetour`, `PatchImm32`, call-site helpers). This tool reads those expectations from the sources offline and checks them against an exe:

```
node tools/patch-bytes-check.ts                       # Steam exe: self-validation, all must be ok
node tools/patch-bytes-check.ts --other "<path>\TS3W.exe" [--ref game-copy/bin/TS3W.exe] [--all]
```

- Extracted statically: `InstallDetour(name, ADDR, BYTES, N, hook)` and `Matches(ADDR, BYTES, N)` with constant addresses (`#define`, `const DWORD`, simple expressions, casts) and named byte arrays or string literals, also `ADDRS[i]` with `BYTES[i]` and local aliases of them; tables of site structs (address field `at`/`addr`/`site` with an expected-bytes field `old`/`pro`/`orig`/`bytes`/`b`/`expect`/`prologue` and optional `len`; a `target`/`callee` without bytes = `E8 rel32` to it; `slot` + `fn` = the dword at the slot holds `fn`). Function-local names resolve to the declaration in scope at the call.
- Other exe: addresses come from the `exe-addr-map.ts` mapping (call targets too); a data slot is found by the one aligned dword outside code holding the mapped `fn`. Kinds: `ok`, `ported` (only rel32 or absolute-pointer operands differ: the source's expected bytes need the other exe's values), `mismatch`, `unmapped`. Patched sites in §2 (rows of a patching kind) without any expectation are `unchecked`; patch calls whose address or bytes are built at run time are `unresolved` (count; listed in the CSV).
- Prints one summary line plus problem rows; every row goes to `out/patch-bytes-check/<exe>.csv` (gitignored: EA bytes).
- Steam (2026-10-31): 3,064 expectations (bytes 2,957 of which 2,705 from the generated `vcallsites*.h`, call 61, slot 46) at 3,062 addresses, all `ok`; unchecked 257 of 494 §2 patched sites; 37 unresolved patch calls. Steam via the mapping (`--other` = the same exe): 3,061 `ok`, 3 `unmapped` (2 slots whose function sits in more than one data dword, the `.data` GC budget immediate `0x01192324`), ~12 s.
- Limits: unchecked sites are mostly helpers that copy prologues or compute `E8` bytes at run time (`[Verify]`'s 58 detours, call-site retargets, private pools) and §2 rows that also list read-only callees; data expectations need a `ref` row or a slot value to map.

### 7.4 Port without the exe: player probe (`tools/port-probe/`)

The EA app exe is encrypted on disk (`.ooa`, `.text` entropy 8.0) and decrypts only at run time, and Rodney does not own it. A player runs a plain PowerShell script at the main menu; it sends back numbers only, and the Rodney-side tools rebuild the §7 outputs from that. No AI on either side up to the problem rows; every tool ends with `AI needed: none` or `AI needed: N rows (see <file>)`.

```
node tools/port-sigs.ts                     # rebuild tools/port-probe/port-sigs.txt from the Steam exe (commit it)
# player: Run-PortProbe.cmd (or Sims3PortProbe.ps1) at the main menu -> Desktop\Sims3PortReport-<sha8>.zip
node tools/port-report.ts <Sims3PortReport-xxxxxxxx.zip> [--questions q.json]
#   -> out/exe-addr-map/<exe>-<sha8>.csv (+ .offsets/.vtables/.candidates/.managed/.problems.csv), same CSV as exe-addr-map
```

- **Signatures** (`port-sigs.ts`, no game bytes): sites = the exe-addr-map list + patch-bytes-check addresses (858 code, 47 data); window +-256 bytes; call rel32 and absolute pointers masked; concrete runs cut into non-overlapping 16-byte tiles, each a 48-bit hash (two murmur3-32) = 3 bits per byte, so the bytes cannot be rebuilt; plus operand positions and kinds (no values). 12,154 tiles, 49,840 operands, 794 KB.
- **Probe** (`Sims3PortProbe.ps1`, PS 5.1 and 7, inline C#, read-only `ReadProcessMemory`, no admin unless the game runs elevated): finds `TS3.exe`/`TS3W.exe`, polls the code entropy until below 7.2 (a progress line every 2 s, fails after 30 s without change), reads the image, then writes: exe identity (size, sha256, file version, PE timestamp, base, `.ooa`, section table with entropy, code sha256); per site `u`/`a`/`-` with the new address, extent and mismatched tiles, plus call targets and absolute pointers in the matched window and displacement/immediate values inside mismatched tiles; fingerprints of the whole code (functions = call targets after padding + vtable slots + IC functions: size, instruction count, 12-class instruction mix, callees, imports by name, string texts <= 120 chars, globals; RTTI class names and vtables; pointer-run vtables with slot functions; IC tables `{fn, "Class::Method"}` with their slot address); every S3SA assembly in `Game\Bin\Gameplay\*.package` (MVID, version, per method IL size, 24-bit IL hash, parameter count, type and name); install context (`skuversion.txt` version lines, EP/SP folders, `Sims` registry product names, Bin loaders/proxies by name, Windows version). User, machine and profile path are scrubbed. `-Questions` answers a follow-up (`insn` = operand numbers of N instructions, `dword`, `string`); `-DumpOut` (dev only, own EA install) writes the decrypted image for `exe-addr-map --other` (checked on the Steam exe: 857 of 857 exact).
- **Rodney side** (`port-report.ts`): map rows as exe-addr-map (exact, masked, offset-changed with `<exe>.offsets.csv`, near, ambiguous, missing with hint, ref / ref-conflict; new kind `partial` = unique but the +-32-byte core differs without an operand explaining it); missing/ambiguous/partial rows placed by function fingerprints (function pairs from IC names, mapped sites, unique strings, unique structure keys, spread over call edges; then a score of shared strings, mapped callees/callers, imports, size and mix) -> `hint` or `near`, `<exe>.candidates.csv`; vtables by slot-function votes (`<exe>.vtables.csv`); data addresses by IC slot name, vtable slot or globals voted over paired functions; assemblies diffed against `game-copy/assemblies` (`<exe>.managed.csv`: size-changed, hash-only, removed, added; methods whose type and name appear in `mods/ts3fixes/src` flagged and counted as AI rows except hash-only).
- Steam vs Steam through the probe's own C# (`-ImageFile`, 2026-10-31): 857 exact + 1 `near` (twin window, same address) + 47 data `ref`, all at the same address, `AI needed: none`; 46,454 functions, 39,373 pairs, 1,826 of 2,099 vtables mapped (the rest share all their slot functions); 10 assemblies same MVID. Limits: no fuzzy re-search (a site whose every anchor tile changed is `missing` until fingerprints place it); IL hashes include metadata tokens (hash-only changes are often renumbering); nested type names lack their enclosing type.

### 7.5 One command: `tools/port-run.ts`

The entry point for a port; §7-§7.4 are its stages. It runs them in order and prints one screen:

```
node tools/port-run.ts --exe "<path>\TS3.exe" [--allow-inferred] [--build] [--ghidra-names]   # decrypted exe (or -DumpOut image)
node tools/port-run.ts --zip Sims3PortReport-xxxxxxxx.zip [--asm <dir>] [same options]        # player probe (§7.4)
```

- **Stages:** map (`exe-addr-map.ts`, or `port-report.ts` for a zip, with `--questions` written for the player), expected original bytes (`patch-bytes-check.ts` `check()` on the exe; for a zip every expectation takes its site's map kind: `ok` only for `exact`, else `unverified`/`inferred`/`unmapped`), `addr-codemod.ts gen` (strict; `--allow-inferred` passes through). One summary line per stage. Probe-only expectations from generated headers (`vcallsites*.h`, 2,701) are skipped, as the codemod skips those headers.
- **Problems:** `out/port/<id>/problems.csv` (`<id>` = exe name + sha8, or the zip name), one row per address with the stages merged: `prio,stage,address,label,kind,candidates,ai,where`. Priority 1 = patch sites (expectations + docs/68 §2 patched sites: a wrong address there is a crash), 2 = hooks and other code, 3 = reads/data; `managed` rows (ts3fixes methods changed in the script assemblies) are 2. `candidates` = the mapped address with its kind, the fingerprint guess with score, or the neighbour `hint`; `where` = every source line naming the address (codemod scan). `ai=no` when a candidate exists (it needs `--allow-inferred` plus the bytes check or the player's answers, not a hunt); `ai=yes` for no candidate, `mismatch`, `ref-conflict` and managed rows. Last line `AI needed: none` or `AI needed: N rows (see <file>)` = the `ai=yes` rows.
- **Identity:** an exe (or a zip whose head names an exe) with the Steam exe's sha256 takes the addresses the map cannot reach (data nobody's matched window reads) as the same address.
- **`--build`** prints, never runs: the table copy to `native\ts3native\out\ts3addr-table.h`, `cmd /c "set CL=/DTS3A_TABLE&& native\ts3native\build.cmd out-port-<id>"`, the `patch-bytes-check.ts --other` re-run (exe only) and a one-job smoke queue (`out/port/<id>/port-smoke.json` = release-check's smoke job with the port `.asi`, for a machine with that exe). While the sources still hold plain literals it says `sources not on TS3A yet: run addr-codemod --apply first (post-Mono refactor)`.
- **`--ghidra-names`** writes `out/port/<id>/ghidra-names.csv` via `tools/port-ghidra-names.ts` (also standalone: `--map <csv> [--candidates <csv>] [--min-score 6] [--other <exe>]`): Steam names from `tools/ghidra/symbols/ts3w-1.67.symbols.csv`, then `docs/data/ic-safety.csv` (ICs), `docs/data/mint-opcodes.csv` (`mint_<op>` handlers) and the map's hook-site labels (`ts3n_<label>`), moved to the new address. `exact`/`masked`/`ref` keep the name; `near`, `offset-changed` and fingerprint guesses (score >= 6, port-report's own bar) get `_guess` and an `[unverified: ported, inferred]` comment. With the exe, every named address the map lacks is mapped too. Apply it to a project that imported the other exe (writes the project, so no `-readOnly`; `force` because the SHA-256 is not Steam 1.67; ImportSymbols also wants image base 0x400000):
  `analyzeHeadless <projectDir> <project> -import <exe> -scriptPath tools/ghidra -postScript ImportSymbols.java out/port/<id>/ghidra-names.csv force` (add `-noanalysis` only when the project is already analysed; `keep` leaves user names alone).
- Steam identity (2026-10-31): `--exe` 857 exact + 172 identity, patch 363 ok, gen 1,012 addresses 0 errors, `AI needed: none`, ~27 s with `--ghidra-names` (4,156 of 4,336 names, 16 `_guess`). `--zip` from the probe's `-ImageFile` report: 315 ok + 47 `unverified` data refs + 1 `inferred` twin; gen 91 rows need `--allow-inferred` (data `ref` rows), all `ai=no`, `AI needed: none`.
- Limits: the zip stage cannot compare bytes (player answers to `questions.json` do that, §7.4); `--build` is not compile-checked (the TS3A refactor is not applied); data addresses no matched window reads stay `gen` rows on a real port.
