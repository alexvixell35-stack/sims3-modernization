## 1. The question

The scan's `overlap` verdict says that a mod and one of our features reach the same game code. It does not say whether anything breaks. A rule turns each finding into one of four outcomes:

- **compatible**: nothing in the way, for the stated reason.
- **caveat**: both work, with a limit the wording names (usually: our fix does not reach one of the mod's own actions).
- **incompatible**: something breaks or one side is lost.
- **not decided**: the scan lacks the fact the rule needs (rescan, or a game test).

A row's `rule` column is the worst outcome over its findings, then the rule ids with counts, worst first, for example `caveat: override-no-base x3, derives x199, override-calls-base x16, off-by-default x8`. `own issues` is added when the known-bad list names the mod. It is a separate flag: it says the mod has a problem of its own, with or without ours, and never changes the outcome.

## 2. Rules

Evidence: **static** = read from the files; **in-game proven** = a game run with the mod exists; **community-reported** = known from players and authors. Full condition, wording and counter-examples are in the JSON file.

### How the facts are read

- **Base call** (`override-*`): the IL of the mod's override is decoded and every `call` (not `callvirt`) target is resolved. A target with the same method name on any type in the mod type's base chain counts, so `base.Cleanup()` into the mod's own intermediate class counts too (that class is assumed to reach the game's). Spot-checked: More Romantic Interactions' cuddle interactions call `InteractionInstance::Cleanup` or their mod base's `Cleanup`, one does not; Buy Takeout's `FoodDeliverySituation.OnServiceStarting` makes 5 calls, none to the base.
- **Module build** (`module-*`): every replaced module's assembly version is `1.0.0.0` in every patch, so it cannot tell. The rule compares member sets instead: the 2009 builds of 343068 and 354513 lack about 7,300 of the 11,087 `Sims3GameplaySystems` types of Steam 1.67, the old 2x Weight and Fitness builds lack about 600-3,600, and every current build (simler90 UPDATE242, xCAS 1.67 / 1.69.43, 2x Weight 1.66 / 1.67 / 1.69) lacks none. The EA app 1.69 script assemblies are not in `game-copy`; the 1.69 builds of xCAS and 2x Weight match the Steam 1.67 member set, so the two editions are assumed to share it (inferred).
- **Changed** (`module-changed`): the IL shape (`managed-callgraph.ts` `ilShape`, compiler-generated names folded as in `tools/mod-method-diff.ts`) of each patched method, all overloads, in the mod's copy against the game's. The text says `changed by the mod` per method.
- **Static copy** (`static-copy`, added 2026-11-22 after the NRaas source audit, docs/318 "Every other NRaas project"): a mod that calls its own static copy of a game step never reaches our hook on the game's method, and nothing derives from the patched type, so the scan used to call it compatible (NRaas Overwatch: `HarvestPlantEx.DoHarvest`, its Harvest replacement's copy of `HarvestPlant.DoHarvest`). Match: name and params (an instance method's copy takes the declaring type first; no-param statics are too common to count), then a call-graph check: when both IL bodies decode, the copy must make at least half of the game method's calls (`Type::method` of call / callvirt / newobj). A static that calls a same-named method of another type is a wrapper (a mod's own `LocalizeString` that forwards to the game's), not a copy. The call-graph check cut the hits from 25 rows to 4 mods (the `LocalizeString`, `OnAgeTransition` and `ParseBuffData` helpers were name matches only). Known miss: Dreamer's `Update` copy (it calls its own copies of the steps, so under half of EA's calls match); the source audit found it. Rule column only; the `verdict` column is unchanged. Self-check fixtures: copy, other params, other name, no params, wrapper, below half the calls, the patched type itself.
- **Hiding copy** (`derives-hides`): only for a non-virtual patched method. A `new` copy of a virtual patched method is no hiding here: the game's virtual calls still reach the patched base (Drinks for your Sims' `SingShowerSong.Cleanup` is such a copy, so Drinks stays `derives`).
- **Keys and tuning**: the bytes of both resources; tuning XML is split into leaf fields (`tag[i]/tag[j]@attr`, `.../#text`). With the game's version at hand each side's changes are compared, else any field both sides set to different values counts as overlap (shortcut, noted in the code).
- **Older rows**: a matrix row the current scan did not read (the 2026-11-02 player folder) gets its rule from its evidence text. The text has no base-call or module facts, so those rows get the `*-unread` rules.

## 4. Mod-vs-mod (Apex ModConflicts)

The same rules decide Apex's pair reports (`pairRule`, and `keyFinding` + `findingRule` for keys):

| Apex level and kind | our rule |
|---|---|
| CONFLICT resource key | `key-same` (Apex would not report), `key-different`, `key-script`, `tuning-disjoint`, `tuning-overlap` |
| CONFLICT core mod | `pair-core-same-module` (incompatible) or `pair-core-other-module` (compatible); an old build is `module-old` |
| CONFLICT assembly | `pair-assembly-copies` |
| CONFLICT interaction | `pair-interaction` (caveat: one version of that action is lost) |
| CONFLICT native hook | `pair-hook-conflict`; coordinated overlaps (INFO) are `asi-standdown` |
| WARNING | `pair-area-hint` (not decided) |
| INFO identical copies | `pair-identical` |

## 6. Gaps

- Static only until the queue runs. `in-game proven` is claimed only for `named` (the test install) and the hang-seen part of `own-issues`.
- Base call: one level. An override that calls base only on some paths counts as calling it; an intermediate mod class is assumed to reach the game's method.
- Module build is judged against Steam 1.67's assemblies; the EA 1.69 member set is inferred to be the same (§2).
- Tuning disjointness without the game's base version treats a field that only one side has as that side's own.
- The pair rules have no scanner here; Apex finds the pairs.
- `docs/COMPATIBILITY.md` and the matrix CSV are not changed on this branch (branch `feature/compat-top500-1122` is still adding rows): the next matrix write (`--matrix`) adds the `rule` column, and the page's column table then needs a `rule` line.

## 7. Resolution: their fix or ours (2026-11-22, branch `feature/compat-resolve-1122`)

Rodney (2026-11-22): where a mod conflicts, use their fix when it is better than ours, make ours win when ours is better, and send per-mod setting fixes to Apex's setup installer. Every caveat and incompatible row of both matrices was compared statically: what the mod's method does (member tokens of its IL: calls, fields, strings, read locally, nothing copied) against what our fix does at the same place, then correctness, crash / hang / save safety, cost, the household rule and the audit evidence (docs/318, `known-bad-mods.json`).

Verdicts: **OURS-BETTER** = our fix is missing for the mod's interactions and can sit around the mod's own code at run time; **THEIRS-BETTER** = the mod fixes the same EA bug better, so our feature would stand down; **EQUAL / COMPLEMENTARY** = no change: the mod has no copy of the bug we fix, or both fixes run side by side; **N/A (old build)** = the mod's copy of a game module is for an older patch: no fix comparison, the player needs the mod's current build.
